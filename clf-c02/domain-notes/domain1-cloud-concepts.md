## 태스크 1.1 AWS 클라우드의 이점

### AWS 한 줄 정의
전 세계 데이터 센터에서 **200개 이상의 서비스**를 제공하는 클라우드. 핵심 가치는 **비용 절감 · 민첩성 향상 · 빠른 혁신**입니다.

### 클라우드 컴퓨팅의 5가지 기준

| # | 기준 | 의미 | AWS에서는 |
|---|---|---|---|
| 1 | **온디맨드 셀프 서비스** | 사람의 개입 없이 필요할 때 직접 프로비저닝 | 콘솔, CLI, API |
| 2 | **광범위한 네트워크 접근** | 네트워크로 리소스에 접근·생성 | HTTP/HTTPS, VPN, SSH |
| 3 | **리소스 풀링** | 여러 고객이 공유하는 대규모 리소스. 정확한 물리 위치는 모름 | 리전·AZ는 선택 가능, 데이터 센터는 AWS가 선택 → **규모의 경제** |
| 4 | **탄력성** | 수요에 따라 확장·축소 | Auto Scaling |
| 5 | **측정 가능한 서비스** | 사용량을 측정해서 요금 청구 | **사용한 만큼만 지불** |

### 고가용성 vs 내결함성 vs 재해 복구

| 구분 | 목표 | 장애 시 다운타임 | 예시 (서버 2대) | 비용 |
|---|---|---|---|---|
| **고가용성 (HA)** | 장애를 **최대한 빨리 복구**해서 가동 시간 최대화 | **짧게 발생할 수 있음** | Active-**Standby** (장애 시 전환, 재로그인 필요할 수 있음) | 중간 |
| **내결함성 (FT)** | 장애가 나도 **계속 동작** | **없음** | Active-**Active** (이미 둘 다 서비스 중) | **높음** |
| **재해 복구 (DR)** | 재해에 **미리 계획**하고 발생 시 복구 절차 실행 | 계획에 따라 다름 | 다른 리전으로 복구 | 전략에 따라 다름 |

> 💡 실무 비유: WebLogic 클러스터 Active-Standby = HA, Active-Active + 세션 복제 = FT, DR 센터 전환 런북 = DR
> 🧠 **HA = 빨리 고친다 / FT = 안 멈춘다 / DR = 미리 계획한다**

### 크기 조정 (Scaling) ⚠️

| 구분 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **수직 (Scale Up)** | 인스턴스를 **더 크게** (t2.micro → t2.medium) | 애플리케이션 수정 불필요 | **재부팅 → 중단**, 비용 증가, 크기 한계 |
| **수평 (Scale Out)** | **같은 크기 인스턴스를 추가** + 로드 밸런서 | 저렴, 고가용성 향상 | **세션 관리** 필요 (스티키 세션 등) |

- **탄력성 (Elasticity)** = **수평 크기 조정 + 자동화**로 수요에 맞게 용량을 늘리고 줄이는 것 (Auto Scaling)

> 🧠 시험 팁: **수직 = 더 큰 것 / 수평 = 같은 것 더 많이 / 탄력성 = 수평 + 자동**

## 태스크 1.2 설계 원칙 (Well-Architected Framework)

> AWS가 제시하는 클라우드 아키텍처 **모범 사례**. 워크로드 점검 도구는 **AWS Well-Architected Tool**.

### 일반 설계 원칙
1. 필요 용량 **추측 중단**
2. **프로덕션 규모**로 테스트
3. 아키텍처 **자동화**
4. 진화하는 아키텍처 허용, 데이터 기반 결정, **게임 데이**로 개선

### 6가지 원칙 (Pillar) ⚠️

| 원칙 | 핵심 질문 | 설계 원칙 키워드 |
|---|---|---|
| **운영 우수성** (Operational Excellence) | 잘 **운영**하고 계속 개선하나? | 코드형 운영, **작고 되돌릴 수 있는 변경**, 절차 자주 개선, 실패 예측, 실패에서 학습 |
| **보안** (Security) | 데이터·시스템을 **보호**하나? | 강력한 자격 증명 기반, **추적성**, 모든 계층 보안, 보안 자동화, **전송 중·저장 시 데이터 보호**, 데이터 수동 처리 최소화, 보안 이벤트 대비 |
| **안정성** (Reliability) | 의도대로 **일관되게 동작**하나? | **장애 자동 복구**, 복구 절차 테스트, **수평 확장**, 용량 추측 중단, 변경 관리 자동화 |
| **성능 효율성** (Performance Efficiency) | 리소스를 **효율적으로** 쓰나? | 고급 기술 대중화, **몇 분 만에 전 세계 배포**, **서버리스** 사용, 실험 자주, 기계적 동조(mechanical sympathy) |
| **비용 최적화** (Cost Optimization) | **최저 비용**으로 가치를 내나? | 소비 모델(사용한 만큼 지불), 전체 효율 측정, 데이터 센터 지출 중단, 비용 분석·**귀속(태그)**, 관리형 서비스 |
| **지속 가능성** (Sustainability) | **환경 영향**을 줄이나? | 영향 파악, 목표 수립, **사용률 극대화**, 효율적인 신규 하드웨어 도입, 관리형 서비스, 다운스트림 영향 축소 |

> 🧠 암기: **"운보안성비지"** (운영·보안·안정성·성능·비용·지속 가능성)

### 원칙 구분 키워드 (시험에서 자주 헷갈림)

| 문제 속 키워드 | 원칙 |
|---|---|
| 자동 복구, 장애 후 복원, 수평 확장으로 가용성 | **안정성** |
| 코드형 운영, 작은 변경, 런북, 운영 개선 | **운영 우수성** |
| 서버리스, 전 세계 배포, 적합한 인스턴스 유형 선택 | **성능 효율성** |
| 사용한 만큼 지불, 비용 추적, 적정 크기 | **비용 최적화** |
| IAM, 암호화, 추적성 | **보안** |
| 탄소, 에너지, 사용률 극대화 | **지속 가능성** |

### 확장성 있는 아키텍처 키워드
- **장애에 대비한 설계** (Design for failure)
- **구성 요소 분리** (Decoupling, 예: SQS)
- **병렬화**: 작업을 가장 작은 단위로 나눠 여러 구성 요소에서 동시에 처리

## 태스크 1.3 마이그레이션 이점과 전략

### AWS CAF (Cloud Adoption Framework) ⚠️
- 클라우드 전환에 필요한 **조직의 역량**을 식별하는 모범 사례 지침

| 구분 | 관점 | 키워드 |
|---|---|---|
| 비즈니스 역량 | **Business** (비즈니스) | 투자 대비 비즈니스 결과 |
| | **People** (인력) | 문화, 교육, 조직 변화 |
| | **Governance** (거버넌스) | 리스크, 비용, 프로그램 관리 |
| **기술 역량** | **Platform** (플랫폼) | 아키텍처, 클라우드 플랫폼 구축 |
| | **Security** (보안) | IAM, 위협 탐지, 데이터 보호 |
| | **Operations** (운영) | 모니터링, 장애 대응, 서비스 수준 |

> 🧠 **"BPG / PSO"** — 기술 관점은 Platform·Security·Operations

**CAF 도입 이점 4가지:** 비즈니스 **위험 감소** · **운영 효율** 향상 · **매출 성장** · **ESG 성과** 향상

**클라우드 도입 단계 (강의 기준):**

| 단계 | 내용 |
|---|---|
| 프로젝트 | AWS로 요구 사항을 충족할 수 있는지 평가 |
| 기초 | 일부 앱 이전, 랜딩 존 구성 |
| 마이그레이션 | 클라우드 운영 역할 정의, **CCoE**(Cloud Center of Excellence) 구축 |
| 재창조 | 모든 신규 프로젝트를 AWS에서 시작 |

> 📌 참고: CAF 공식 문서의 전환 여정 단계는 **구상(Envision) → 조정(Align) → 시작(Launch) → 확장(Scale)**입니다. 두 용어 모두 알아 두세요.

### 7가지 마이그레이션 전략 (7R) ⚠️

| 전략 | 별칭 | 의미 | 예시 |
|---|---|---|---|
| **Retire** (사용 중지) | | 더 이상 필요 없는 앱 폐기 | 미사용 레거시 시스템 |
| **Retain** (유지) | | 소스 환경에 그대로 둠 (아직 준비 안 됨) | 규제상 온프레미스 유지 |
| **Rehost** (리호스팅) | **Lift & Shift** | **변경 없이** 그대로 이전 | Tomcat VM → EC2 |
| **Relocate** (재배치) | | 대량 서버를 하이퍼바이저 수준에서 이동 | VMware → VMware Cloud on AWS |
| **Repurchase** (재구매) | **Drop & Shop** | 다른 제품·SaaS로 교체 | 자체 CRM → Salesforce |
| **Replatform** (리플랫포밍) | **Lift, Tinker & Shift** | **일부 최적화**하며 이전 | 자체 설치 Oracle → **RDS** |
| **Refactor** (리팩터링) | 재설계 | **클라우드 네이티브**로 재구성 | 모놀리식 → Lambda·마이크로서비스 |

> 🧠 변경 정도: **Rehost (없음) < Replatform (일부) < Refactor (전면)**

### 마이그레이션 서비스 선택 예시 (강의 문제)

| 상황 | ✅ 정답 | ❌ 오답 이유 |
|---|---|---|
| 금융 데이터, **짧은 지연 시간**, 데이터가 계속 변함 | **EFS + RDS** | S3는 VPC 밖이라 지연 증가 가능, Snowball Edge는 대량 오프라인 이전용 |
| **NoSQL**, 확장성·빠른 속도 | **DynamoDB** (키-값·문서, JSON) | RDS·Aurora는 관계형, Redshift는 분석용, S3는 객체 스토리지 |
| SQL Server **Standard**, **비용 최적화**, 라이선스 관리 원치 않음 | **SQL Server Standard 포함 Windows AMI로 EC2** | RDS는 관리형이라 더 비쌈, **Aurora는 SQL Server 미지원** (MySQL·PostgreSQL만) |
| 대량 데이터 오프라인 이전 | **Snowball** | |
| DB 이전·복제 | **DMS** | |

### 백업·보관
- **S3 Glacier 계열** = 가장 저렴한 보관용 스토리지. 단, **검색 비용과 검색 시간**을 고려해야 함

## 태스크 1.4 클라우드 경제성

### TCO (총 소유 비용) 4가지 구성 요소

| 구성 요소 | 의미 | 예시 |
|---|---|---|
| **OpEx** (운영 비용) | 일상적으로 계속 나가는 비용 | 전기, 토너, 소모품 |
| **CapEx** (자본 비용) | 한 번 구매해 수년간 쓰는 자산 | 건물, 서버, 비상 전원 |
| **인건비** | 온프레미스 운영 인력 | NOC 엔지니어, 서버 설치·장애 대응 |
| **소프트웨어 라이선스** | 이전 시 라이선스 영향 | BYOL 가능 여부, AWS 포함 라이선스로 전환 |

> 🧠 시험 팁: **온프레미스 → AWS 이전 = CapEx(자본 비용)가 가변 비용(OpEx)으로 전환**

### 비용 최적화 설계 원칙 (Well-Architected)
1. **소비 모델** 채택 (사용한 만큼 지불)
2. 전반적인 **효율성 측정**
3. **데이터 센터 운영에 지출 중단** (차별화되지 않는 일)
4. 비용·사용량 **분석 및 귀속** (→ 비용 할당 태그 ⚠️)
5. **관리형 서비스**로 TCO 절감

### 클라우드로 비용을 줄이는 방법
- **적정 크기 조정** (Right-sizing): 최대 수요 기준 프로비저닝 대신 벤치마크·성능 테스트로 크기 결정
- **자동화**: 수요에 맞춰 수평 확장·축소
- **규정 준수 범위 축소**: 데이터 세분화·맞춤 보고로 감사 시간 절약
- **관리형 서비스** 사용: 운영 인력·시간 절감

## 시험 팁 한 장 요약

| 키워드 | 정답 |
|---|---|
| 수요 예측 불필요, 사용한 만큼 지불 | 클라우드 이점: **용량 추측 중단 / 가변 비용** |
| 대량 구매로 단가 하락 | **규모의 경제** |
| 장애 시 빠르게 복구 (약간의 다운타임 허용) | **고가용성** |
| 장애에도 다운타임 없음 | **내결함성** |
| 재해 대비 사전 계획 | **재해 복구** |
| 더 큰 인스턴스로 변경 | **수직 확장** |
| 같은 인스턴스 추가 + ELB | **수평 확장** |
| 수평 확장 + 자동화 | **탄력성** |
| 자동 복구, 수평 확장 | Well-Architected **안정성** |
| 서버리스, 전 세계 배포 | Well-Architected **성능 효율성** |
| 에너지·탄소 | Well-Architected **지속 가능성** |
| CAF 기술 관점 | **Platform · Security · Operations** |
| 변경 없이 이전 | **Rehost** |
| 일부 최적화하며 이전 (예: RDS로) | **Replatform** |
| 클라우드 네이티브로 재설계 | **Refactor** |
| SaaS로 교체 | **Repurchase** |
| 온프레미스 → AWS 비용 구조 변화 | **CapEx → 가변 비용** |
